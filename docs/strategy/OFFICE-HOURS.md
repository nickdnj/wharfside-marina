## Problem Statement

The honest problem is **four overlapping problems stacked on top of each other**, and Nick's PRD does not rank them. They have to be ranked, because the right tool for each is different.

1. **Operational gap (real, low-grade).** Wharfside has no system. Slip assignments live in Kathy Vanecek's email, spreadsheets, and institutional memory at ECI. Required slip-owner documents (COI, registration, indemnification) are collected ad-hoc. There is no patron-facing site. This is real but it has been "working" for 30+ years, which means the pain is chronic, not acute.

2. **Specialized gap (real, narrow).** AppFolio handles billing and accounting beautifully and is not going anywhere. It does not model marina-specific economics — slip-fit, MLW depth, premium/standard tiers, transient capacity caps, resort-fee scenarios, buy-in scenarios. Nothing AppFolio offers will close this. **This is the only gap that genuinely requires custom software.**

3. **Governance gap (real, the most under-named).** The board makes pricing decisions in a vacuum. There is no scenario-modeling capability — "if we move to a resort-fee model, what does annual revenue look like?" / "if we restructure non-resident pricing, what's the delta?" This is the gap Nick keeps gravitating toward, and it is the most defensible reason to build something custom. **It is also the gap with the weakest validated demand.**

4. **Personal/portfolio motivation (real, legitimate, must be named).** Nick is a builder. He has already conceptually drifted from "ops tool for Kathy" toward "Dockwa replacement." The competitive research cache reads like a SaaS go-to-market plan, not a board-internal tool spec. **If this motivation is not named, it will keep gravitationally pulling scope back to v1 even after a v0.2 "scope correction."**

**Ranked by operational severity for Wharfside the marina (not Nick the founder):** 2 > 3 > 1 > 4.
**Ranked by Nick's actual energy:** 4 ≈ 3 > 2 > 1.

These two rankings disagree. That is the central tension of this project.

## Demand Evidence

The PRD is honest about this section, and the honesty should be louder. The evidence is thin.

- **Founder motivation: STRONG.** Nick is on the board, wants visibility, wants a portfolio piece, has the skill. This is real and sufficient to start a project — but it is not sufficient to justify the scope written.
- **ECI / Kathy demand: NOT VALIDATED.** The PRD calls Kathy the "primary admin user" and marks Q-G4 (ECI adoption commitment) as `[HIGH RISK]`. No artifact exists where Kathy has said "yes, I would use this instead of email and AppFolio." Until that artifact exists, the project's primary user is hypothetical. **This is the single biggest hole in the plan.**
- **Board demand for scenario modeling: NOT VALIDATED.** Has Linda (Treasurer, CPA) asked for a pricing modeler? Has the board ever rejected a pricing proposal because they couldn't see the alternatives? If Linda has been running pricing analysis in Excel and finds it adequate, the Pricing Engine pillar collapses.
- **Slip-owner demand for a portal: NOT VALIDATED, PROBABLY WEAK.** The user base skews 50s–80s, NJ residents, low digital literacy. They currently email Kathy. The PRD assumes they'd prefer a portal. Boater forums consistently show low engagement with marina portals when an email channel already exists. The patron site has clearer value (Google-able rules + emergency contacts) than the slip-owner dashboard.
- **Transient request volume: NOT VALIDATED, PROBABLY LOW.** Wharfside has no transient marketplace footprint. Per the PRD itself, transient activity is "limited or zero." If true, the entire Transient Request Workflow pillar is theater for a use case that happens 2-4 times per year.
- **Marina Restoration is a known catalyst.** Restoration changes slip layout and is DEP-approved. The board will need *some* tool to model the new slip mix and reissue assignments. That is a concrete forcing event — but it is also a one-time event, not a recurring need.

**Net read:** Demand evidence is strong for (a) the patron site and (b) a pricing/scenario modeler used by Nick and Linda (n=2 board users). Demand for (c) the ECI-facing slip ops tool and (d) the slip-owner portal is *assumed*, not *demonstrated*.

**Primary user candidates, ranked by validated demand:**

| **Dockmaster (mobile lookup)** | Unknown — is there even a dockmaster role today? | Medium | Low (rare need) |

**Narrowest wedge that proves value:**

The honest narrowest wedge is **the Pricing Scenario Modeler + Patron Site**, NOT the slip ops portal. Reasoning:

- The modeler has a guaranteed user (Nick + Linda) and a guaranteed forcing event (Marina Restoration → new pricing structure decisions in late 2026 / early 2027).

**This inverts the PRD's MVP scope.** The PRD treats Slip Assignment + Document Collection as Pillars 1-2 and the Pricing Engine as a later pillar. The actual demand evidence says **start with the Pricing Engine + Patron Site and treat Slip/Doc tools as Phase 2 (conditional on ECI buy-in).**

## Approaches Considered

### Approach A: Lean Stitched Stack

- **Summary**: Airtable (slip inventory, assignments, doc expirations) + Box/Drive (uploaded docs) + Squarespace (patron site) + Mailchimp (renewal reminders). Excel/Google Sheets for any pricing analysis. Done.
- **Effort**: 3 weekends of setup, ~$60/month ongoing
- **Risk**: Low. No code maintenance. Bus-factor-proof — any board successor can take over.
- **Pros**: Fast, cheap, ECI is more likely to use Airtable than a custom web app (she already uses spreadsheets). Covers Pillars 1, 2, 3 acceptably.
- **Cons**: **Does not solve the Pricing Engine / Scenario Modeler at all.** Airtable can't model what-if scenarios across resort fees, buy-in tiers, tier restructuring. No audit trail on pricing decisions. Slip-fit enforcement is honor-system, not validated.

### Approach B: Phased Custom Build (Pricing Engine + Patron Site MVP)

- **Summary**: Invert the PRD scope. MVP is the **Pricing Scenario Modeler + Patron Site** — the two pieces with validated users and no off-the-shelf substitute. Defer Slip Assignment + Doc Collection to Phase 2, contingent on Kathy saying yes.
- **Effort**: MVP 50-80 hours (modeler is the heavy piece; patron site is mostly Markdown + Next.js). Phase 2 adds 60-100 hours.
- **Risk**: Medium. The Modeler has a real user (Nick + Linda). The Patron Site has no adoption risk. Phase 2 has ECI risk, but you don't commit to Phase 2 until you have her commitment.
- **Pros**: Builds the thing that *only* a custom build can do. Doesn't waste effort on pillars (slip ops, slip-owner portal) where adoption is unverified. Patron Site provides immediate public value with zero adoption risk. Versioned slip config can be modeled inside the Pricing Engine without committing to a full ops tool.
- **Cons**: Defers the visible "Wharfside has a real marina app" feeling. Doesn't help Kathy directly until Phase 2. Pricing Engine logic is the hardest part and risks Master Deed / Cutolo gotchas if not vetted early.

### Approach C: Full Custom Build (all four pillars at once)

- **Summary**: Build everything in the PRD — Slip Ops + Doc Collection + Patron Site + Pricing Engine + Transient Workflow — ship Spring 2027.
- **Effort**: 150–250 hours over 6–9 months.
- **Risk**: High. ECI adoption is unverified. Slip-owner adoption is probably weak. Transient workflow is theater. Bus factor risk compounds with feature surface area.
- **Pros**: Complete vision shipped. Portfolio piece.
- **Cons**: Long timeline; validates nothing along the way; if Kathy passes on adoption in month 4, half the build is orphaned; restoration may shift slip layout mid-build.

### Approach D: Dockwa + AppFolio glued via Zapier

- **Summary**: Pay Dockwa $5K/yr, accept the misfit, Zapier between Dockwa and AppFolio for paid-up status sync.
- **Effort**: Setup ~$2K + 20 hours of integration work.
- **Risk**: Medium-High. Two systems of truth (Dockwa for slips, AppFolio for billing). Constant reconciliation pain. Dockwa rate updates require Marina Success Manager involvement (their documented limitation).
- **Pros**: Vendor-supported. Off-the-shelf slip and doc tooling.
- **Cons**: **Wrong tool.** Dockwa is built for transient marketplace + payments. Wharfside has no transient market and AppFolio owns payments. The misfit is structural. Also: zero Pricing Modeler capability.

### Approach E: AppFolio extension / Property Manager Plus + custom fields

- **Summary**: Work entirely within AppFolio. Use custom fields for slip metadata. Use AppFolio's owner portal for doc upload. Build nothing external except a static patron site.
- **Effort**: Negotiation with ECI + a static site weekend.
- **Risk**: Medium. AppFolio's flexibility on marina-specific data is unverified. Pricing modeling is impossible inside AppFolio.
- **Pros**: Maximum ECI familiarity. Zero new system to maintain.
- **Cons**: **AppFolio cannot model pricing scenarios.** Customization gated by ECI's plan tier and willingness. Patron site is still a separate build.

## Recommended Approach: B — Inverted MVP (Pricing Modeler + Patron Site First)

Build a phased custom app, but **invert the PRD's pillar ordering** to match the actual demand evidence.

### Phase 0: Validation (4-6 weeks, zero code)

Do not write code. Do these in parallel:

1. **Sit with Kathy at ECI for 60 minutes.** Show her wireframes for the slip-ops + doc-collection portal. Ask directly: "If we build this, will you use it instead of email?" If she says no or hedges, **kill Pillars 1-2 permanently** and ship only the Pricing Modeler + Patron Site.
2. **Sit with Linda for 60 minutes.** Walk through what the Pricing Modeler should do. Confirm her actual current process. Validate the scenarios she actually wants to model (resort fee variants, buy-in tiers, premium/standard restructuring). Get her to commit to being the primary user.
3. **One question to 6-8 slip-owners (informal):** "Would you upload your insurance to a website, or do you prefer emailing Kathy?" If 5 of 8 say "email is fine," the slip-owner portal is dead weight.
4. **Cutolo 30-minute call.** Confirm Master Deed Sec 24(B) does not block any pricing structure the modeler might propose. Get the constraint list IN WRITING before the Pricing Engine architecture commits.
5. **Restoration timeline check.** Get the actual slip-count-and-layout lock-in date from Meeco/Falcon. The modeler must support both pre-restoration and post-restoration configs (versioning is mandatory).

**Phase 0 ends with a written go/no-go decision** that explicitly names which pillars are alive and which are killed.

### Phase 1: Pricing Modeler + Patron Site MVP (60-90 hours, Sept 2026 target)

- **Pricing Scenario Modeler** (the hard part):
  - Versioned slip configuration (pre/post restoration)
  - Slip metadata: tier, MLW depth, power/water, position
  - Multiple holder types: Resident discount %, Non-Resident full, Transient capacity cap
  - Scenario engine: define a rate card (base rate, resort fee toggle, buy-in toggle, tier multipliers) → produce projected annual revenue + per-slip breakdown + comparison table against current rate card
  - Draft → PDF export → emailed to board → mark Approved → Active (the human approval flow stays human; the app just records state)
  - Audit log of every scenario, every export, every approval mark
- **Patron Site**:
  - Markdown-driven Next.js or static
  - Rules, contact (ECI, after-hours, dockmaster), emergency procedures, marina map, FAQ, downloadable forms, restoration status, seasonal notices
  - Public, no login
- **Auth**: Magic link for Nick + Linda + any board officer reviewing scenarios. No slip-owner accounts yet.
- **Hosting**: Cloud Run + Cloud SQL OR Vercel + Supabase. ~$30-50/month.

### Phase 2: Slip Ops + Doc Collection — CONDITIONAL on Phase 0 Kathy commitment (60-100 hours, Spring 2027)

Build only if Kathy committed in Phase 0. If she didn't, ship the stitched alternative (Airtable + Box) for doc collection and stop.

- Slip inventory + assignments (mostly reused from the Pricing Modeler's data model)
- Document upload + expiration tracking + reminder emails (Mailchimp or Postmark)
- Compliance dashboard
- Slip-owner portal — **only if Phase 0 slip-owner question came back positive**. Otherwise, doc upload is admin-side (Kathy uploads what slip-owners email her, app tracks expirations).

### Phase 3: AppFolio integration, OCR expiration extraction, mobile dockmaster view, etc. — defer indefinitely

Only build these if a specific operational pain emerges. Do not pre-build.

### Why this is the right path

1. **It matches demand evidence.** Pricing Modeler has guaranteed users (Nick + Linda). Patron Site has zero adoption risk. Slip ops has unverified ECI demand. Don't build for unverified demand.
2. **It validates the riskiest premise (ECI adoption) BEFORE committing to it.** Phase 0 is cheap; Phase 2 is conditional on a real answer.
3. **It builds the only thing custom software actually justifies.** A Pricing Scenario Modeler doesn't exist off-the-shelf, doesn't exist in AppFolio, doesn't exist in Dockwa. Everything else can be stitched.
4. **It survives restoration.** Versioned slip configs are mandatory anyway for the modeler.
5. **It survives Nick rolling off the board.** A small Next.js app with the Pricing Modeler is a self-contained tool the next Treasurer can use or retire. A full ops tool with 5 admin users and a portal is a maintenance albatross.
6. **It does not bait the scope creep.** No transient workflow theater. No slip-fit enforcement engine for an n=0 problem. No mobile dockmaster app for a phantom dockmaster.

### The risk that would change the recommendation

**If Kathy says in Phase 0 — unprompted and unambiguously — "yes, I would use this every day instead of email,"** then Approach B's Phase 2 becomes Phase 1B (parallel build) and the project scope becomes the full PRD. That is the single fact that flips the recommendation. Until she says it, default to the inverted MVP.

## Risks (called out explicitly)

1. **ECI adoption risk (CRITICAL).** Without Kathy's buy-in, half the PRD's pillars are dead on arrival. Phase 0 question to her is the make-or-break gate.
2. **Bus factor.** If Nick rolls off in 2027/2028, the maintenance burden falls on... no one. Mitigate by keeping the codebase small (Pricing Modeler + Patron Site = ~3K LOC if disciplined) and the data exportable. Stitched fallback should be documented as the "if Nick disappears" plan.
3. **Restoration timing.** Slip layout may shift mid-build. Versioned slip configs handle this but add complexity. Lock the restoration date with Meeco/Falcon before Phase 1 architecture.
4. **Master Deed Sec 24(B) constraints.** Marina-loan covenants may limit what the Pricing Modeler can legally propose. Cutolo review is a hard prerequisite, not optional.
5. **Scope creep from "build it for resale."** Nick already drifted there in the research cache. Fence it. Write into the README: "This is an internal tool for Wharfside Manor. It is not a commercial product. Any feature must be justified by Wharfside operational need, not by hypothetical SaaS market fit."
6. **AppFolio reconciliation.** Two systems of truth (modeler/ops here, billing in AppFolio) means manual reconciliation forever unless live API ships. Live API is a 2-4 month bureaucratic detour. Accept the manual reconciliation as the long-term operating cost.
7. **Board governance friction.** Pricing changes go through board approval out-of-band. The app records state ("Draft" → "Approved" → "Active") but does not automate the human process. This is correct — do not try to model board votes in software.
8. **Pricing Engine complexity is non-trivial.** Multi-tier rate cards × multiple holder types × resort fee toggles × buy-in scenarios × versioned slip configs = the most complex part of the build. Spike on this in Phase 0 with paper models before committing to Phase 1 architecture.
